1. System overview

The Banking Knowledge Agent answers technical questions about a banking platform — ATM and self-service banking, digital banking, cards, payments, APIs, integrations, configuration and incident troubleshooting — and backs every answer with sources.

The objective is not a chatbot. It is a demonstration of production-oriented AI engineering: retrieval, an agent loop, tool use, guardrails, testing, observability and containerisation, each behind a clean boundary.

4. Components

Built today

ComponentWhat it does
app/main.py
create_app()		 Application factory. Loads settings, configures logging, builds the FastAPI instance, stores settings on app.state, mounts routers, and logs startup/shutdown through a lifespan handler. A factory (rather than a bare module-level singleton) is what makes the app testable with overridden configuration.
app/core/config.py
Settings		 All configuration as one typed, frozen, validated object read from BKA_* environment variables. get_settings() is lru_cached so the environment is parsed once.
app/core/logging.py Configures structlog + the stdlib bridge. Writes human-readable output to stdout locally, JSON in production, and rotating JSON files to logs/. Sets up a separate bka.trace logger with propagate = False.
app/core/tracing.py
@traced, @traced_async		 Wraps a function so each call emits a structured trace event — qualified name, duration in ms, ok/error outcome — to logs/traces.log. Arguments are deliberately never recorded.
app/api/dependencies.py SettingsDep resolves settings from request.app.state rather than the cached global, so the app factory stays the single source of truth.
app/api/routes/health.py GET /health — a pure liveness check returning status, service name, version and environment. It touches no downstream system.
app/knowledge/models.py
DocumentMetadata, KnowledgeDocument		 The document contract. Every document carries document, domain, component, version and type, validated at load time. Domain and DocType are closed Literal sets and unknown front-matter keys are rejected, so a typo fails the load instead of silently creating a domain nothing filters on.
app/knowledge/loader.py
load_knowledge_base()		 Reads Markdown + YAML front matter from data/knowledge/ into validated KnowledgeDocument objects. Strict by design: a malformed, mislabelled, duplicated or empty document raises rather than being skipped. Returns documents in sorted order so indexing runs are reproducible.
app/rag/models.py
Chunk, EmbeddedChunk, ScoredChunk, RetrievalResult		 The pipeline's data contracts. The one to know is Chunk, which separates content (the passage as written, shown to a human and to the LLM) from embedding_text (the same passage with a "Document title — Section" prefix, which is what actually gets embedded). RetrievalResult carries the outcome and the reason for it, so an empty result is informative rather than just empty.
app/rag/chunker.py
chunk_documents()		 Splits documents on Markdown ## headings, with the size budget measured in the embedding model's own tokens. Oversized sections are broken at paragraph or table-row boundaries; a split table re-carries its header row in every part. Guarantees no chunk exceeds the model's window.
app/rag/embeddings.py
Embedder protocol		 Two implementations behind one protocol. SentenceTransformerEmbedder runs all-MiniLM-L6-v2 locally, loading it lazily so importing the module stays cheap. HashingEmbedder is deterministic and dependency-light, and is what the fast test suite runs on. Both return L2-normalised vectors, so cosine similarity is a dot product everywhere downstream.
app/rag/vectorstore.py
VectorStore protocol, InMemoryVectorStore		 Exact cosine search over one NumPy matrix, persistable to disk. Filters are applied before scoring. The saved manifest records which model built the index and refuses to load it under a different one.
app/rag/retriever.py
Retriever.retrieve()		 Question → embedding → similarity search → threshold → scored chunks and deduplicated sources. Composes an Embedder and a VectorStore, both injected. No LLM anywhere, so retrieval quality is measurable on its own.
app/rag/pipeline.py
build_index(), load_retriever()		 The offline path end to end, plus a SHA-256 fingerprint of the corpus so a stale index is refused rather than silently served.
app/rag/__main__.py CLI: build, search, demo, calibrate. Indexing is a build step, so it needs a way to be run; calibrate exists so the score threshold can be re-derived from data rather than inherited as a magic number.

6. RAG flow

BUILT — Stages 2 & 3

Why RAG at all? An LLM does not know this platform, and fine-tuning is the wrong tool for documentation that changes. Retrieval keeps the knowledge base editable, makes every answer citable, and constrains the model to material we control.

The knowledge base (Stage 2, built)

15 synthetic Markdown documents, ~7,800 words, describing a fictional Meridian banking platform. They are written specifically for this project: no vendor documentation, branding or confidential material is reproduced.

Why Markdown + YAML front matter rather than JSON or a database: the body is exactly the text that gets chunked and embedded, it stays readable and reviewable in a diff, and the metadata travels with the content it describes.

Why the loader is strict. A silently skipped document becomes an answer the agent cannot ground — a far harder fault to diagnose than a failed load. So missing front matter, invalid YAML, an unknown domain, an unrecognised key, a document_id that disagrees with its filename, a duplicate id, an empty body, or an empty knowledge directory all raise.

Documents are data, not instructions. From Stage 5 their text is fed to an LLM, which makes them an untrusted input surface. The corpus is written as pure technical reference prose, and the test suite scans it for secret-shaped values and card-number-shaped digit runs on every run.

Worked example — the output is real

$ python -m app.rag search "Why would an ATM transaction fail after card authentication?"

  1. 0.790  ATM Transaction Lifecycle — Why a transaction can fail after card authentication
            atm / TransactionSwitch v4.2 · atm/atm-transaction-lifecycle.md
  2. 0.682  ATM Transaction Lifecycle — Why a transaction can fail after card authentication
            atm / TransactionSwitch v4.2 · atm/atm-transaction-lifecycle.md
  3. 0.627  Card Authentication and Authorisation — The authorisation decision
            cards / AuthorizationService v4.2 · cards/card-authentication.md
  sources: 2 document(s)

$ python -m app.rag search "What is the capital of France?"

  NO MATCH — nothing scored above 0.25 of 115 chunks.

Note results 1 and 2: the same section, split into two chunks, both retrieved. That is the chunker's table/paragraph splitting and the store's ranking agreeing with each other. Because sources deduplicates by document, the citation list still says two documents, not five — five chunks of one document is one piece of evidence to a reader, and a citation list that repeats it five times looks like five.

Why metadata travels all the way down

Metadata is not decoration. Every Chunk carries the complete DocumentMetadata of its source, which is what lets the system say "per ATM Transaction Lifecycle (TransactionSwitch v4.2)" instead of "somewhere in the docs", and what makes filters={"domain": "payments"} possible. Citations are addressed by document_id, which is why the loader insists it match the filename, and source_path is normalised to POSIX so a citation reads identically on Windows and inside a container.

The score floor is what makes honesty possible. Without it, "what is the weather tomorrow?" still returns the five least-bad banking chunks — and an LLM handed five confident-looking banking passages writes a confident banking answer. The floor turns "nothing here is relevant" into an empty result the agent can refuse on. See §20 for how the number was derived.

The grounding rule

The agent must not invent technical facts. When the knowledge base does not contain enough evidence, the correct output is an explicit statement to that effect — not a plausible guess. In a banking support context a confident wrong answer is worse than "I don't have that documented."

What is exposed

Execution information is surfaced — retrieval performed, documents used, tool called, tool result, final answer. Hidden chain-of-thought is not exposed.

Example questions the agent must handle

  • Why would an ATM transaction fail after card authentication?
  • What component handles card authentication?
  • Which API is used for payment authorisation?
  • How would I troubleshoot a failed cash withdrawal?
  • What configuration controls transaction limits?

The rule: the LLM receives the retrieved context, never the whole knowledge base. That is what keeps cost, latency and prompt-injection surface bounded — and it is the difference between RAG and stuffing a prompt.

The abstraction covers prompt management, system instructions, question handling, context injection, response generation, error handling (timeouts, rate limits, malformed responses) and environment-based configuration. Tests use a mock provider, so the suite runs offline, deterministically, and at zero API cost.

10. Vector database

BUILT

Accessed through a VectorStore protocol — add(), search(), count(), clear() — so the implementation is replaceable. The shipped implementation, InMemoryVectorStore, is one NumPy matrix.

InMemoryVectorStore
  _matrix   ndarray (115, 384) float32, contiguous, all rows unit length
  _chunks   list[Chunk]        row i of the matrix ↔ _chunks[i]

  search(q, k, filters)
     indices = rows permitted by filters          ← pre-filter, not post
     scores  = _matrix[indices] @ q               ← one BLAS matvec
     top     = argpartition(-scores, k)[:k]       ← O(n), no full sort
     return sorted top as ScoredChunk

Why brute force, and when that stops being true

115 vectors × 384 dimensions is ~176 KB. Scoring all of them is a single matrix-vector product — tens of microseconds, orders of magnitude below the cost of embedding the query, never mind an LLM call. An approximate index (HNSW, IVF) buys sub-linear scaling by spending recall, and there is no scaling problem here to spend recall on.

The honest crossover is somewhere around 105–106 vectors, or when the index no longer fits comfortably in one process's memory, or when several replicas need to share writes. At that point the VectorStore protocol is the thing that makes it a one-class change rather than a rewrite.

The on-disk format, and the two guards on it

FileContentsWhy this format
vectors.npyThe (n, 384) float32 matrixCompact, exact, and loads without parsing.
chunks.jsonChunk text + full metadataHuman-readable. When retrieval misbehaves the first question is "what is actually in the index?", and that should be answerable with a text editor.
manifest.jsonformat version, model id, dimension, chunk count, corpus fingerprint, build timeThe guard rail — see below.
Both guards exist because their failure mode is silent.
  • Wrong model. Searching an index built by model A with a query embedded by model B does not raise — the vectors just live in unrelated spaces, and you get confident, plausible-looking nonsense. So the manifest pins the model id and dimension, and load() refuses a mismatch.
  • Stale index. If a document changed after indexing, answers stay fluent and citations still resolve — nobody notices the agent quoting a procedure that was edited last week. So the manifest carries a SHA-256 fingerprint of the corpus (metadata and body), checked on load.
Neither would surface in the output. That is exactly why they are checked explicitly.

BKA_LOG_DIR=logs
BKA_LOG_TO_FILE=true
Two settings deliberately default to "ask the model". BKA_CHUNK_MAX_TOKENS is unset by default so the chunker uses the embedding model's own window, and the vector dimension is never configured at all — it is read off the loaded model. Hardcoding either would be correct today and silently wrong the moment the model changes, and both failures show up as bad search results rather than as an exception.

.env.example is committed and documented. .env is git-ignored and must never be committed. Secrets come from the environment only — never hardcoded, never defaulted to a real value.

13. Observability

BUILT (foundation) · request tracking Stage 10

Two sinks, deliberately separate

SinkContents
logs/app.logApplication events — startup, shutdown, requests, errors. JSON lines, size-rotated.
logs/traces.log@traced function traces via the bka.trace logger, which has propagate = False so traces never leak into the application stream.

A trace event

{"event": "trace",
 "function": "app.main.create_app",
 "duration_ms": 12.481,
 "outcome": "ok",
 "level": "info",
 "timestamp": "2026-09-03T12:30:20.303038Z"}
Arguments are never logged. A traced function may receive a card number, a customer identifier or an API key. Only the qualified name, duration and outcome are recorded.

Planned for Stage 10

Request ID propagated through structlog.contextvars; question, retrieval latency, retrieved documents, LLM latency, tool calls, tool latency, errors, and overall response latency — all as queryable fields.

Known constraint: tracing and FastAPI

@traced must not decorate FastAPI route handlers. FastAPI resolves a handler's postponed annotations against that function's __globals__; a wrapper defined in app/core/tracing.py resolves them against the tracing module instead, so dependency annotations silently degrade into query parameters and requests fail with 422. This was caught by the test suite in Stage 1. Route handlers are traced by request middleware in Stage 10 — which is the architecturally correct layer for it anyway.

Why two embedders, and why that is a testing decision as much as a design one. Almost every RAG test runs on the deterministic HashingEmbedder: no 90 MB download, no warm cache, no machine-dependent floating point, and the whole suite finishes in ~30 s. Those tests assert mechanics. A separate, integration-marked file asserts quality against the real model, because mechanics cannot prove that a question finds the right passage. A mock would not have done this job: a mock proves the calls happen, not that the numbers are right. Running the real pipeline on a different real embedder proves the decoupling is genuine rather than aspirational.

Temp directory: a project-local --basetemp

pyproject.toml sets --basetemp=.pytest_tmp, so tmp_path never touches %LOCALAPPDATA%\Temp\pytest-of-<user>.

Why — a real failure, not a precaution. pytest hardens its default temp root by stripping inherited ACLs, leaving only SYSTEM, Administrators and OWNER RIGHTS. When that directory gets created by an elevated process whose owner resolves to BUILTIN\Administrators, a normal non-elevated run of the same user has no ACE at all and every tmp_path test dies with PermissionError: [WinError 5]. It happened here: 96 errors in a normal shell, while an elevated shell passed all 240 — because the elevated shell had access through the Administrators ACE. And because pytest reuses pytest-of-<user> across runs, the broken state persisted.

An explicit basetemp fixes both halves: it inherits the repository's permissions rather than Temp's, and pytest deletes and recreates it every session, so a bad state cannot outlive one run.

The wider lesson, which applies to any tooling that runs commands for you: a green run under different privileges is not evidence the suite passes for the person who will run it.

Stage 11 adds an evaluation framework over a small dataset of realistic banking questions with expected evidence, measuring retrieval accuracy, answer grounding, hallucination resistance and tool selection — because "the tests pass" and "the answers are correct" are different claims.

16. Security

BUILT (foundations) · full review Stage 13

In place today

  • Secrets from environment variables only — never hardcoded, never a real default.
  • .env, *.pem, *.key, secrets/ and logs/ are git-ignored.
  • Traced function arguments are never logged.
  • Pydantic validates every request and response at the boundary.
  • Server binds to 127.0.0.1 by default, not 0.0.0.0.
  • Front matter is parsed with yaml.safe_load, so a document cannot construct arbitrary Python objects.
  • The test suite scans the whole corpus on every run for secret-shaped values (private keys, assigned passwords or API keys) and card-number-shaped digit runs.
  • Knowledge documents are treated as untrusted data, not instructions — they become LLM input in Stage 5.
  • The embedding model runs locally: no document text and no user question leaves the machine during indexing or retrieval. That is a data-privacy property, not just a cost one — a hosted embedding API would send every question and every document to a third party.
  • data/vectorstore/ is git-ignored. It contains no secrets, but it is a derived artefact and committing it would let the index and the documents drift apart in version control.
  • The retrieval log records the question text. That is a deliberate, recorded decision: these are technical support queries about a synthetic platform, not customer data. It is flagged in retriever.py for reassessment in Stage 13 if the deployment context ever changes.

To be assessed and documented in Stage 13

Authentication, authorisation, secrets management, input validation, prompt-injection risk, MCP tool security, data privacy, rate limiting, LLM and tool failure handling, logging risks, and dependency security. Lightweight protections where practical — no unnecessary enterprise infrastructure for a portfolio project.

Prompt injection is the live risk for this class of system. Retrieved documents and tool results are untrusted input to the model. They must be treated as data, never as instructions.

19. Design decisions

DecisionReasoning
App factory (create_app()) rather than only a module-level app Tests can build an application with overridden settings. A bare singleton would force tests to mutate global state.
Settings from app.state, not the cached global The factory stays the single source of truth. The first version used Depends(get_settings) and the health test caught it immediately — the endpoint reported local while the app was configured as test.
structlog from Stage 1, not Stage 10 Retrofitting structured logging over string logs means rewriting every call site. The cost now is near zero.
Separate trace sink with propagate = False Per-function traces are high volume. Mixed into the application log they would bury the events that matter operationally.
Trace arguments are never recorded A traced function may receive card data, customer identifiers or API keys. Name, duration and outcome are enough to diagnose latency and failure.
@traced is not applied to route handlers It breaks FastAPI's annotation resolution (see §13). Request tracing belongs in middleware, which is the correct layer regardless.
Frozen settings Configuration that mutates at runtime is a debugging trap.
Pinned dependencies Local, CI and Docker builds resolve to identical versions.
mypy strict With many interfaces (LLM, vector store, tools), static checking catches contract drift between layers before runtime does.
uv for the virtual environment Practical, not architectural: the stdlib venv module is missing from the system Python on this machine, and a virtualenv-created environment segfaulted on importing structlog and httpx. A uv-created environment works.

20. Decision records (per stage)

What this section is for. §19 is the one-line summary. This is the long form: for each significant decision, what was chosen, why, what was rejected and why, and what the choice costs. Where a number appears it was measured on this corpus with this model, not taken from a blog post — the measurement commands are given so any of it can be re-derived.

Stage 3 — RAG pipeline

3.1   Embedding model: local all-MiniLM-L6-v2

Chosen. sentence-transformers running all-MiniLM-L6-v2 on the local CPU. 384 dimensions, 256-token window, ~90 MB, no API key, no per-query cost, no network after the first download.

Why. The whole reason to embed rather than keyword-match is paraphrase. A support engineer types "customer says money left the account but no cash came out"; the document that answers it is titled "Troubleshooting a Failed Cash Withdrawal" and shares almost none of those words. Only a semantic model bridges that. It is now a passing test, not a claim.

RejectedWhy
Hosted embedding API
OpenAI, Voyage, Cohere		 Best quality and trivial to run, but: it is a paid per-query call, it needs a key in every environment including CI, it sends every document and every question to a third party, and it makes the test suite depend on the network. The project rule is no paid external API without explicit sign-off — and here the free local option was good enough that the spend was not justified.
Lexical retrieval
TF-IDF / BM25, zero new dependencies		 Genuinely tempting, and stronger on this corpus than the usual dismissal suggests: the text is dense with distinctive identifiers (TransactionSwitch, ATM-4021, LimitService) that lexical matching nails. It would have added no dependencies and kept the image tiny. Rejected because it cannot do the paraphrase case above, which is the realistic support query. Worth noting as the one rejected option that would likely improve results if added alongside the embedder — hybrid search is the natural next step.
A larger local model
e.g. all-mpnet-base-v2, bge-large		 Better retrieval, but 3–5× the size and latency for a 15-document corpus where MiniLM already separates on-topic from off-topic by 0.27 cosine. Buying quality that is not currently the bottleneck.

What it costs. ~250 MB of PyTorch in the dependency tree and a ~90 MB model download on first run — by far the largest thing in this project. That is a real Docker-image and cold-start cost to account for in Stage 12, and it is the price paid for the paraphrase capability above.

3.2   Chunk boundaries: Markdown ## headings

Chosen. Split on the section headings the author already wrote. A section becomes one chunk unless it is too big for the model.

Why. A heading is a human's explicit statement of where one topic ends and the next begins — strictly better information than any character count. And it was checked rather than assumed: measuring all 15 documents gives 108 sections, 32–411 tokens, median 99. They are already chunk-sized.

RejectedWhy
Fixed-size sliding window
the default recipe: ~512 chars, 50 overlap		 It would cut through the middle of numbered troubleshooting procedures and Markdown tables — and this corpus is mostly procedures and tables. "Step 4 of 6" severed from steps 1–3 is not a useful retrieval result. The generic recipe ignores structure that is right there in the document.
One chunk per document Documents run 457–670 words, which is 700–1,100 tokens — 3–4× the model's window. Every document would be truncated to its first quarter. Also the wrong retrieval granularity: the answer to "why does it fail after authentication" is one section, and returning the whole document buries it.
Merging small sections together Planned, then dropped after measuring: the smallest section in the corpus is 32 tokens, and there are no degenerate one-line fragments to merge. The complexity was not earned. Worth revisiting only if a future document introduces them.

Re-derive: the section-size distribution comes from split_sections() plus Embedder.count_tokens.

3.3   Budget measured in the model's own tokens the finding that changed the design

Chosen. The chunker asks the embedder for both the limit (max_tokens) and the length of any text (count_tokens). No word counts, no character counts, no hardcoded 256.

Why — and this started as a mistake. The first plan was a word budget, converted with the usual "~0.75 words per token" rule of thumb. Measuring the actual ratio on this corpus killed it:

tokens per word, across 108 sections
   min 1.13   mean 1.61   p90 2.07   max 2.82

worst offender:  146 words  →  411 tokens

The cause is the domain. Identifiers like SWX-7001 and switch.downstream_timeout_ms shatter into many word-pieces, so the densest sections are the ones a word budget underestimates most — and those are exactly the config-key and error-code tables engineers search for.

Why this matters more than it looks. all-MiniLM-L6-v2 does not raise when input exceeds 256 tokens. It truncates and returns a perfectly normal-looking vector. A too-long chunk is therefore a passage that has quietly stopped being findable, with nothing anywhere to indicate it. A word-based budget would have silently amputated the six densest sections in the corpus and the system would have looked like it was working.

So the invariant — no chunk exceeds the model's window — is asserted as a test against the real model, not just trusted. Current worst case: 251 of 256.

RejectedWhy
Word or character budgetMeasured above: off by up to 2.8× on the exact content that matters most.
Hardcoding 256Correct today, silently wrong the moment the model changes — and failing as bad results rather than an error. The number is read off the loaded model instead.
Using tiktokenIt tokenises for OpenAI models. MiniLM is a BERT word-piece model with a different vocabulary, so the counts would be confidently wrong. The right tokenizer is the one attached to the model doing the embedding.

3.4   Oversized tables split row-wise, header repeated

Chosen. When a section over the budget is a Markdown table, split it between rows and re-carry the header and separator rows into every part.

Why. Of the six sections that exceed the window, most are tables — Timeout and retry keys (366 tokens), POST /v1/payments/authorise (411), The keys (260). These are the highest-value retrieval targets in the whole corpus. And a table fragment without its header is unreadable:

split naively                      split with the header repeated
─────────────────────────          ──────────────────────────────
| DEV-6002 | Cassette   |          | Code     | Meaning  | Class |
|          | empty      |          |---|---|---|
| DEV-6004 | Dispenser  |          | DEV-6002 | Cassette empty | Operational |
|          | jam        |          | DEV-6004 | Dispenser jam  | Hardware    |

  columns mean nothing               self-contained and citable
RejectedWhy
Treat tables as plain textLoses the column names on every part but the first — see above.
Skip tables entirelyThey are the best content in the corpus, not an inconvenience.
Convert tables to prose before embeddingWould embed better, but needs an LLM pass over the corpus at index time: paid, non-deterministic, and it puts generated text into the citation path. Not worth it for six sections.

3.5   Contextual prefix: embedding_text ≠ content

Chosen. What gets embedded is "{document title} — {section heading}\n\n{content}". What gets stored, shown and cited is content alone.

Why. Chunking orphans text. This is a real chunk from the corpus:

"Reversals are retried up to `switch.reversal_retry_count` times.
 Reversals are idempotent: the same transaction reference may be sent again safely."

It never says ATM, never says TransactionSwitch, never says withdrawal. Embedded as it stands, a question phrased in those terms will not find it. Prefixing "ATM Transaction Lifecycle — Reversals" puts the entity names back into the vector. Keeping the prefix out of content keeps the human-facing text and the LLM's context clean, and stops the prefix being cited as though it were part of the document body. The cost is honest and accounted for: the prefix spends part of the token budget, so the chunker reserves it before splitting rather than after.

RejectedWhy
Embed the raw contentThe orphaning problem above.
Prepend to content itselfSimpler by one property, but it pollutes what a human reads and what the LLM is given, and it makes the citation text include a header the source document does not contain.
Full contextual retrieval
an LLM writes a bespoke summary per chunk		The published technique, and better. It is also ~115 LLM calls per index rebuild — paid, slow, and non-deterministic, so two builds of the same corpus would differ. The title-and-heading prefix captures most of the benefit for zero cost. Revisit if retrieval quality ever becomes the bottleneck.

3.6   Vector store: brute-force NumPy, not a vector database

Chosen. Exact cosine search over one in-memory (115, 384) float32 matrix, behind a VectorStore protocol.

Why. Scoring the entire corpus is a single BLAS matrix-vector product over ~176 KB — tens of microseconds, orders of magnitude below the cost of embedding the query, let alone an LLM call. An ANN index exists to buy sub-linear scaling by sacrificing recall; there is no scaling problem here to spend recall on. Choosing the simple thing is the decision, and the protocol is what makes it reversible.

RejectedWhy
ChromaThe obvious "just use a vector DB" pick, and it would work. But it brings its own embedding-function abstraction and its own persistence model, which means two competing opinions about how embedding works in one codebase — and hiding the seam this stage is meant to demonstrate.
FAISSExcellent at scale. At 115 vectors an HNSW graph is slower to build than the exhaustive search it replaces, and it is approximate: it would trade recall for a speed-up that is already invisible.
pgvector / Qdrant / WeaviateA container, a network hop and an operational dependency for a project whose requirement is to run locally and offline. Right answer in production, wrong answer here.

When this stops being right. Roughly 105–106 vectors, or when the index no longer fits comfortably in one process, or when several replicas need shared writes. Then it is one class implementing VectorStore; the retriever, agent and API do not change.

3.7   Cosine similarity, via normalised dot product

Chosen. Vectors are L2-normalised at encode time, so cosine similarity is exactly matrix @ query.

Why. Not merely convenient — correct. all-MiniLM-L6-v2 is trained with a cosine objective, so cosine is the metric the vector space was actually built for. Normalising once at encode time also means nothing downstream has to remember to do it, which is one fewer silent-wrongness opportunity.

RejectedWhy
Euclidean distanceOn unit vectors it is monotonically equivalent to cosine, so it ranks identically — but with an extra subtraction and square root, and a score that no longer reads as "similarity in [-1, 1]". No benefit.
Dot product on unnormalised vectorsVector length then becomes a relevance signal, which it is not: longer chunks would systematically outrank shorter ones regardless of content.

3.8   Metadata filters applied before scoring

Chosen. Restrict the candidate rows first, then score and rank within them.

Why. Post-filtering is the classic retrieval bug. Ask for the top 5 chunks and then keep only the payments ones, and you can easily be left with zero — not because the corpus lacks payments material, but because five ATM chunks happened to outrank it. Pre-filtering always returns the best k of the permitted set. There is a test named after exactly this case.

An unknown filter field raises rather than matching nothing, for the same class of reason: {"damain": "atm"} would silently return an empty result that looks identical to "the knowledge base has no answer".

Cost. The filter is an O(n) Python scan over chunk metadata — negligible at 115 chunks, and the wrong shape at 106. A real vector store pushes this into the index as a payload filter; that is a property of the replacement, not of the interface.

3.9   A minimum-score floor of 0.25 — calibrated, not guessed

Chosen. A passage must score ≥ 0.25 cosine to be returned. Below that, retrieval returns nothing.

Why. Vector search always returns its k nearest rows. Ask "what is the weather tomorrow?" and it will hand back the five least-bad banking chunks with no complaint — and an LLM given five confident-looking banking passages will write a confident banking answer. The floor is the single mechanism that converts "nothing here is relevant" into an empty result Stage 5 can honestly refuse on.

How the number was derived. Not from a blog post — cosine scores are a ranking signal, not a calibrated probability, and the useful range differs per model and per corpus. It was measured (python -m app.rag calibrate):

Top-1 cosine score, best match per question

  on-topic  (10 questions)   min 0.388   median 0.775   max 0.819
  off-topic ( 5 questions)   min 0.032   median 0.104   max 0.122

  separation: +0.266   (worst on-topic 0.388 − best off-topic 0.122)
  midpoint:    0.255
  configured:  0.250

The two distributions are cleanly separated, and 0.25 sits in the gap with margin on both sides. A test asserts the separation still holds and that the configured floor still sits between the two — so if a future document or a model swap collapses the gap, the suite says so.

RejectedWhy
No floor at allEvery question gets evidence, including questions the corpus cannot answer. This is the direct route to a confidently wrong answer, which in a banking support context is worse than no answer.
A number from a tutorial (0.7 is the usual one)Would reject every genuine result here — the worst on-topic question scores 0.388. Scores are not comparable across models or corpora.
Return top-k and let the LLM judgeDefers a cheap deterministic check to an expensive non-deterministic one, and the failure mode is the model rationalising the irrelevant context it was handed. Worth adding as well in Stage 5; not instead.

Known limitation, stated plainly. Ten on-topic and five off-topic questions is a small sample, and they were written by the same person who wrote the corpus. The threshold is defensible, not proven. Stage 11's evaluation set is where it gets tested properly.

3.10   The index is an offline build artefact

Chosen. python -m app.rag build writes data/vectorstore/. The application loads it; it does not build it.

Why. Embedding the corpus takes seconds and needs hundreds of megabytes of model resident. Doing it per process would make startup slow, make every container replica repeat identical work, and — worst — make a document edit invisible until someone restarts something. Building once and loading is also what lets replicas share one index in Stage 12.

The artefact is git-ignored: it is derived from data/knowledge/, and committing it would both put a binary blob in every diff and allow the index and the documents to drift apart in version control with nothing to notice.

get_retriever() is the convenience path — it loads, and rebuilds only on the three recoverable conditions (no index, wrong model, stale). Anything else still fails loudly rather than being papered over by a silent rebuild.

3.11   Two guards whose failure mode is silence

Chosen. The index manifest records the model id, the vector dimension, an on-disk format version and a SHA-256 fingerprint of the corpus. All four are checked on load.

Why. Both of the failures they catch are invisible in the output, which is the only reason they justify their code:

  • Wrong model. Query vectors from model B against an index built by model A do not error. The two spaces are simply unrelated, so the search returns well-formed, plausible, wrong results. Nothing about the answer looks off.
  • Stale index. If a document changed after indexing, answers stay fluent and every citation still resolves to a real file. The only symptom is the agent quoting a procedure that was edited last week — which nobody notices.

The fingerprint covers metadata as well as body text, so bumping a component version in front matter invalidates the index too. Freshness checking costs a few milliseconds of re-reading the corpus, against the cost of serving confidently outdated banking procedures.

3.12   Two embedders behind one protocol

Chosen. SentenceTransformerEmbedder for real use; HashingEmbedder — deterministic, dependency-light, non-semantic — for the fast test suite.

Why. Two reasons, and the second is the interesting one. Practically, it keeps ~200 tests offline, deterministic and finishing in ~30 s with no model download and no warm cache. Architecturally, running the entire pipeline on a genuinely different embedder is the proof that the decoupling is real. A claim that the model is swappable is worth nothing; a test suite that swaps it is worth something.

Query and document embedding are separate methods even though MiniLM treats them identically, because asymmetric models (E5, BGE, most hosted retrieval models) require different query: / passage: prefixes — and retrofitting that distinction later would mean re-indexing everything.

RejectedWhy
Mock the embedderA mock proves the calls happen. It proves nothing about the numerics — normalisation, dimensions, ranking — which is where retrieval actually goes wrong.
Use the real model everywhereA slow suite that needs a warm Hugging Face cache to run at all. Quality tests need it; ranking, filtering and persistence tests do not.
Python's built-in hash() for the hashing embedderGenuine trap: PYTHONHASHSEED randomises string hashing per process, so an index written by one run would be unreadable by the next. Uses blake2b instead.
