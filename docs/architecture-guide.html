1. System overview

The Banking Knowledge Agent answers technical questions about a banking platform — ATM and self-service banking, digital banking, cards, payments, APIs, integrations, configuration and incident troubleshooting — and backs every answer with sources.

The objective is not a chatbot. It is a demonstration of production-oriented AI engineering: retrieval, an agent loop, tool use, guardrails, testing, observability and containerisation, each behind a clean boundary.

3. Technology stack & why

Each technology has one architectural job. Nothing is here because it is fashionable.

TechnologyJobStage
Python 3.12The language with the mature LLM, embedding and vector-store ecosystem.1
FastAPIAsync HTTP API with typed models, dependency injection and OpenAPI documentation generated from the code — the schema can never drift from the implementation.1
Pydantic v2Validation at the system boundary. Malformed input fails at the edge with a clear 422 instead of propagating into the agent.1
pydantic-settingsTyped, environment-based configuration. Invalid config fails at startup, not at 3am. Keeps secrets out of source.1
structlogLogs are structured events with fields, not formatted prose. Stage 10 needs retrieval_ms, llm_ms, request_id as queryable fields — that is only possible if logging is structured from day one.1
uvicornASGI server for FastAPI's async request handling.1
pytestTest suite, including async API tests via httpx + TestClient.1
ruffFormatter and linter in one fast tool.1
mypy (strict)Static type checking. Catches interface drift between layers before runtime.1
Vector storeSimilarity search over document chunks. Behind an interface so the implementation can be swapped.3
Embedding modelTurns text into vectors so questions can be matched to documents by meaning, not keywords.3
LLM providerGenerates the natural-language answer from retrieved context. Behind an abstraction — the app is never coupled to one vendor.4
MCPA standard protocol for exposing tools to an agent, so tools are a versioned contract rather than ad-hoc function calls.6
DockerReproducible local runtime; the same image everywhere.12

4. Components

Built today

ComponentWhat it does
app/main.py
create_app()		 Application factory. Loads settings, configures logging, builds the FastAPI instance, stores settings on app.state, mounts routers, and logs startup/shutdown through a lifespan handler. A factory (rather than a bare module-level singleton) is what makes the app testable with overridden configuration.
app/core/config.py
Settings		 All configuration as one typed, frozen, validated object read from BKA_* environment variables. get_settings() is lru_cached so the environment is parsed once.
app/core/logging.py Configures structlog + the stdlib bridge. Writes human-readable output to stdout locally, JSON in production, and rotating JSON files to logs/. Sets up a separate bka.trace logger with propagate = False.
app/core/tracing.py
@traced, @traced_async		 Wraps a function so each call emits a structured trace event — qualified name, duration in ms, ok/error outcome — to logs/traces.log. Arguments are deliberately never recorded.
app/api/dependencies.py SettingsDep resolves settings from request.app.state rather than the cached global, so the app factory stays the single source of truth.
app/api/routes/health.py GET /health — a pure liveness check returning status, service name, version and environment. It touches no downstream system.

6. RAG flow

PLANNED — Stages 2 & 3

Why RAG at all? An LLM does not know this platform, and fine-tuning is the wrong tool for documentation that changes. Retrieval keeps the knowledge base editable, makes every answer citable, and constrains the model to material we control.

Indexing (offline, once per document change)

Synthetic banking documents (data/knowledge/)
   │
   ▼  loader — attach metadata
{document, domain, component, version, doc_type}
   │
   ▼  chunker — split, preserving metadata on every chunk
Chunks
   │
   ▼  embedding model
Vectors
   │
   ▼
Vector store

Retrieval (per question)

Question
   │
   ▼  same embedding model  ← must match indexing, or search is meaningless
Query vector
   │
   ▼  similarity search (top-k)
Relevant chunks
   │
   ▼
Sources: document, domain, component, version, score

Metadata is not decoration. It is what lets the system say "per ATM Transaction Processing v2.1, §Authentication" instead of "somewhere in the docs", and it enables filtered retrieval later (e.g. restrict to domain = payments).

The grounding rule

The agent must not invent technical facts. When the knowledge base does not contain enough evidence, the correct output is an explicit statement to that effect — not a plausible guess. In a banking support context a confident wrong answer is worse than "I don't have that documented."

What is exposed

Execution information is surfaced — retrieval performed, documents used, tool called, tool result, final answer. Hidden chain-of-thought is not exposed.

Example questions the agent must handle

  • Why would an ATM transaction fail after card authentication?
  • What component handles card authentication?
  • Which API is used for payment authorisation?
  • How would I troubleshoot a failed cash withdrawal?
  • What configuration controls transaction limits?

8. MCP flow

PLANNED — Stage 6

Why MCP? RAG answers "what do the documents say?". Tools answer "what is the system doing right now?". MCP makes those tools a declared, versioned, transport-agnostic contract instead of ad-hoc functions bolted to the agent.

Knowledge vs. live data. A document says how a component should behave; a tool says how it is behaving. The answer must keep these distinguishable so an engineer can tell documentation from observation.

9. LLM interaction

PLANNED — Stage 4 
app/agent  ──▶  LLMProvider (protocol)  ──▶  concrete provider
                      ▲                          │
                      │                          ▼
              app depends on this          vendor SDK, API key
              interface only               from the environment

The rule: the LLM receives the retrieved context, never the whole knowledge base. That is what keeps cost, latency and prompt-injection surface bounded — and it is the difference between RAG and stuffing a prompt.

The abstraction covers prompt management, system instructions, question handling, context injection, response generation, error handling (timeouts, rate limits, malformed responses) and environment-based configuration. Tests use a mock provider, so the suite runs offline, deterministically, and at zero API cost.

10. Vector database

PLANNED — Stage 3

Accessed through a VectorStore protocol — add(chunks), search(query_vector, k, filters) — so the implementation is replaceable. Local development uses an embedded store requiring no server; the same interface admits a managed vector database in production without touching the agent or API layers.

12. Configuration

BUILT

One typed Settings object, read from BKA_* environment variables (optionally seeded from a local .env), validated by Pydantic and frozen. Invalid configuration fails loudly at startup.

BKA_ENVIRONMENT=local        # local | test | production
BKA_HOST=127.0.0.1
BKA_PORT=8000
BKA_LOG_LEVEL=INFO
BKA_LOG_FORMAT=console       # console locally, json in Docker
BKA_LOG_DIR=logs
BKA_LOG_TO_FILE=true

.env.example is committed and documented. .env is git-ignored and must never be committed. Secrets come from the environment only — never hardcoded, never defaulted to a real value.

13. Observability

BUILT (foundation) · request tracking Stage 10

Two sinks, deliberately separate

SinkContents
logs/app.logApplication events — startup, shutdown, requests, errors. JSON lines, size-rotated.
logs/traces.log@traced function traces via the bka.trace logger, which has propagate = False so traces never leak into the application stream.

A trace event

{"event": "trace",
 "function": "app.main.create_app",
 "duration_ms": 12.481,
 "outcome": "ok",
 "level": "info",
 "timestamp": "2026-09-03T12:30:20.303038Z"}
Arguments are never logged. A traced function may receive a card number, a customer identifier or an API key. Only the qualified name, duration and outcome are recorded.

Planned for Stage 10

Request ID propagated through structlog.contextvars; question, retrieval latency, retrieved documents, LLM latency, tool calls, tool latency, errors, and overall response latency — all as queryable fields.

Known constraint: tracing and FastAPI

@traced must not decorate FastAPI route handlers. FastAPI resolves a handler's postponed annotations against that function's __globals__; a wrapper defined in app/core/tracing.py resolves them against the tracing module instead, so dependency annotations silently degrade into query parameters and requests fail with 422. This was caught by the test suite in Stage 1. Route handlers are traced by request middleware in Stage 10 — which is the architecturally correct layer for it anyway.

15. Docker

PLANNED — Stage 12

A Dockerfile and Compose setup so the whole system runs locally with one command, no cloud infrastructure required. Container config comes from environment variables (BKA_LOG_FORMAT=json), health checks use /health, and synthetic knowledge data stays available inside the image or a mounted volume.

16. Security

BUILT (foundations) · full review Stage 13

In place today

  • Secrets from environment variables only — never hardcoded, never a real default.
  • .env, *.pem, *.key, secrets/ and logs/ are git-ignored.
  • Traced function arguments are never logged.
  • Pydantic validates every request and response at the boundary.
  • Server binds to 127.0.0.1 by default, not 0.0.0.0.

To be assessed and documented in Stage 13

Authentication, authorisation, secrets management, input validation, prompt-injection risk, MCP tool security, data privacy, rate limiting, LLM and tool failure handling, logging risks, and dependency security. Lightweight protections where practical — no unnecessary enterprise infrastructure for a portfolio project.

Prompt injection is the live risk for this class of system. Retrieved documents and tool results are untrusted input to the model. They must be treated as data, never as instructions.

18. Extension points

The point of the seams: each of these should be an additive change, not a redesign.

To add…Touch…
A new knowledge sourceA loader implementation. Chunking, embedding and retrieval are unchanged.
A new banking domainDocuments + metadata. No code change.
A new MCP toolOne tool module + registration. The agent discovers it.
A different LLM providerOne class implementing LLMProvider. Nothing else.
A different vector storeOne class implementing VectorStore.
A different embedding modelOne class implementing the embedder interface (re-index required).

19. Design decisions

DecisionReasoning
App factory (create_app()) rather than only a module-level app Tests can build an application with overridden settings. A bare singleton would force tests to mutate global state.
Settings from app.state, not the cached global The factory stays the single source of truth. The first version used Depends(get_settings) and the health test caught it immediately — the endpoint reported local while the app was configured as test.
structlog from Stage 1, not Stage 10 Retrofitting structured logging over string logs means rewriting every call site. The cost now is near zero.
Separate trace sink with propagate = False Per-function traces are high volume. Mixed into the application log they would bury the events that matter operationally.
Trace arguments are never recorded A traced function may receive card data, customer identifiers or API keys. Name, duration and outcome are enough to diagnose latency and failure.
@traced is not applied to route handlers It breaks FastAPI's annotation resolution (see §13). Request tracing belongs in middleware, which is the correct layer regardless.
Frozen settings Configuration that mutates at runtime is a debugging trap.
Pinned dependencies Local, CI and Docker builds resolve to identical versions.
mypy strict With many interfaces (LLM, vector store, tools), static checking catches contract drift between layers before runtime does.
uv for the virtual environment Practical, not architectural: the stdlib venv module is missing from the system Python on this machine, and a virtualenv-created environment segfaulted on importing structlog and httpx. A uv-created environment works.
